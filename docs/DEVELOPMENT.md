# Developing SchwarMAX

Rules for everyone (people and coding agents) who changes this repository. Read this before your
first commit.

## Branches

| branch | what it is | who commits |
|---|---|---|
| `main` | the published code | **nobody**: it changes only by a reviewed merge from `developing-code` |
| `developing-code` | all development, shared by every workstream | every workstream |

## Layout

```
SchwarMAX/                      the repository root: the SHARED package (model.py, integrates.py, ...)
├── example/                    the published examples (as on main) + shared data: the mock IFU data,
│                               the Git-LFS N-body snapshot, and git-ignored run outputs
├── SchwarMAX-Nbody/            workstream: the PROJECTED (line-of-sight) scheme, tested on the N-body mock
├── SchwarMAX-<name>/           workstream: one folder per new application (e.g. three velocity
│                               components) -- its notebooks, scripts, mock-data builders and tests
└── docs/                       DEVELOPMENT.md (this file), one dev log per workstream
```

A workstream owns its own folder. **The package at the root is shared**, so every workstream uses
and extends the same source code.

## The shared package: add, never erase

1. **Add, don't change.** New behaviour goes in a new function, a new module, or a new keyword
   argument whose default reproduces the old behaviour exactly. Never change the signature, the
   defaults or the numerical result of an existing function.
2. **Never delete or rename** an existing function, argument or module. If something is obsolete,
   say so in its docstring and leave it in place.
3. **Bug fixes that change existing numbers** are the one exception. Make each one a commit of its
   own whose message says so. Re-pin the regression gate in the same commit, and record it in every
   workstream's dev log.
4. **Register new capabilities** in `model.SCHWARMAX_FEATURES` (e.g. `'velocities_3d'`), and have
   notebooks assert on it. An outdated copy of the package then fails at import, not hours into a run.
5. **Audit before committing.** This shows every line your staged change removes from the shared
   package. It should be empty, or contain only the lines you meant to replace:

   ```bash
   git diff --cached -U0 -- '*.py' ':!SchwarMAX-*' ':!example' | grep '^-[^-]'
   ```

## The regression gate

```bash
cd SchwarMAX-Nbody && python test_regression_projected.py      # ~2 min, ~4 GB, CPU
```

It runs both exponential-disc notebooks of the projected scheme on a small library, and requires the
likelihood to reproduce values pinned to 0.01 in logL. It must pass **before any commit that touches
the shared package**, from any workstream. Each workstream also keeps its own smoke tests in its own
folder.

## Two agents, one working folder

All workstreams share the branch and the working folder, so:

- **Stage explicit paths only:** `git add SchwarMAX-Nbody/foo.py model.py`. Never use
  `git add -A`, `git add .` or `git commit -a`, because they sweep in another agent's unfinished
  files.
- **Commit only your own folder,** plus your additions to the shared package.
- **Never run `git checkout`, `git switch`, `git stash`, `git reset` or `git clean`** in the shared
  folder. Each one rewrites files another agent may be editing.
- **`git pull --rebase` before `git push`.** Never force-push.
- **Run outputs are git-ignored** (`example/` outputs, `SchwarMAX-*/figures/`); keep it that way.
  Large inputs go through Git LFS (see `.gitattributes`) or are regenerated by a script.

## Logs

Each workstream appends to its own log, `docs/devlog_<workstream>.md` (e.g. `devlog_projected.md`).
With one file per workstream, the logs never conflict in a merge. When your change affects the
shared package, add a line to every workstream's log.

## Running on Colab

Upload the repository folder to `My Drive` as `SchwarMAX`. The notebooks locate it themselves, find
the package at the root and the data in `example/`.
